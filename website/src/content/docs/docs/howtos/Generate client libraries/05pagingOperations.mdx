This doc details what emitters will generate for paging operations.

## Using next link to indicate how to get the next page

Next link is an absolute url returned by the paging operation, which indicates how to get the next page.
If the response does not return a next link, it indicates the last page of results.
Next link should be annotated in the response model with `@nextLink`.

There are two ways to indicate a paging operation with `@nextLink`:

1. Use `@list`, `@nextLink` and `@items`

<ClientTabs>

```typespec
@list op listWithPage(): UserList;

model User {
  id: string;
  name: string;
}

model UserList {
  @pageItems
  value: User[];

  @nextLink
  nextLink?: url;
}
```

```python
class User(_model_base.Model):
    id: str = rest_field()
    name: str = rest_field()

def list_with_page(self, **kwargs: Any) -> ItemPaged["_models.User"]:
    ...
```

```csharp
public virtual Pageable<User> ListWithPage(CancellationToken cancellationToken = default);
```

```typescript
export interface ListWithPageOptionalParams extends OperationOptions {}
// JS CodeGen api layer
export function listWithPage(
  context: Client,
  options: ListWithPageOptionalParams = { requestOptions: {} },
): PagedAsyncIterableIterator<User>;

// JS CodeGen classical client layer
export class TestServiceClient {
  listWithPage(
    options: ListWithPageOptionalParams = { requestOptions: {} },
  ): PagedAsyncIterableIterator<User>;

```

```java

```

## Using continuation token to indicate how to get the next page

A continuation token is a string returned by a paging operation, which is used as a parameter value for the paging operation to get the next page.
If the response does not return a continuation token, it indicates the last page of results.
The request parameter that corresponds to the continuation token value in the paging operation should be decorated with `@continuationToken`. Similarly, the response property that contains the continuation token value should also be decorated with `@continuationToken`.

1. Continuation token in query parameter and response body.

<ClientTabs>

```typespec
@list
op listWithPage(@query @continuationToken continuationToken?: string): UserList;

model User {
  id: string;
  name: string;
}

model UserList {
  @pageItems
  value: User[];

  @continuationToken
  continuationToken?: string;
```

## Advanced

### Parameterized next links (against guidelines)

:::danger
Parameterized next links are against guidelines. Please don't follow this unless explicitly told to do so
:::

In very rare cases, there are cases of next links that require parameterization. These cases exist outside of the Azure guidelines for paging, but must be supported for legacy reasons.

In cases like this, you may use the special scalar type `Azure.Core.Legacy.parameterizedNextLink`. You can specify which parameters must be reformatted into the next link. Your emitted SDK will handle the reformatting based on the tsp definition

```tsp
model ListCertificateOptions {
  includePending?: string;
}
model Certificate {
  name: string;
}
model Page {
  @pageItems items: Certificate[];
  @nextLink nextLink: Azure.Core.Legacy.parameterizedNextLink<[
    ListCertificateOptions.includePending
  ]>;
}
```

### Force an operation to be treated as pageable (Legacy)

:::caution
The `@markAsPageable` decorator is legacy functionality that should **only** be used for brownfield services where an operation returns a list but was not originally annotated with paging decorators. **New services should use `@list` with `@pageItems` and `@nextLink` instead.**
:::

The `@Azure.ClientGenerator.Core.Legacy.markAsPageable` decorator forces an operation to be treated as a paging operation even if it does not use `@list`. The operation must return a model that contains a property decorated with `@pageItems` or a property named `value`.

<ClientTabs>

```typespec
import "@azure-tools/typespec-client-generator-core";

using Azure.ClientGenerator.Core.Legacy;

model Widget {
  id: string;
  name: string;
}

model WidgetList {
  value: Widget[];
  nextLink?: url;
}

@route("/widgets")
@get
@markAsPageable
op listWidgets(): WidgetList;
```

```python
# The operation is generated as a paging method:
def list_widgets(self, **kwargs: Any) -> ItemPaged[Widget]:
    ...
```

```csharp
// @markAsPageable is primarily a Python/Java customization.
// C# emitter may handle paging detection differently.
```

```typescript
// @markAsPageable is primarily a Python/Java customization.
// TypeScript emitter may handle paging detection differently.
```

```java
// The operation is generated as a paging method:
public PagedIterable<Widget> listWidgets() { ... }
```

```go
// @markAsPageable is primarily a Python/Java customization.
// Go emitter may handle paging detection differently.
```

</ClientTabs>

### Prevent an operation from being treated as pageable (Legacy)

:::caution
The `@disablePageable` decorator is legacy functionality that should **only** be used for brownfield services where an operation follows paging patterns but should not be generated as a paging method. **New services should not need this decorator.**
:::

The `@Azure.ClientGenerator.Core.Legacy.disablePageable` decorator prevents an operation from being treated as pageable, even if it follows paging patterns (e.g., uses `@list` with `@pageItems`).

<ClientTabs>

```typespec
import "@azure-tools/typespec-client-generator-core";

using Azure.ClientGenerator.Core.Legacy;

model Widget {
  id: string;
  name: string;
}

model WidgetList {
  @pageItems
  value: Widget[];

  @nextLink
  nextLink?: url;
}

@route("/widgets")
@list
@disablePageable
op listWidgets(): WidgetList;
```

```python
# The operation returns the raw response model, not a paging iterator:
def list_widgets(self, **kwargs: Any) -> WidgetList:
    ...
```

```csharp
// C# emitter may handle paging detection differently.
```

```typescript
// @disablePageable is primarily a Python/Java customization.
// TypeScript emitter may handle paging detection differently.
```

```java

```

### Override next-link HTTP verb (Legacy)

:::caution
The `@nextLinkVerb` decorator is legacy functionality that should **only** be used for brownfield services where the next-page endpoint uses a different HTTP verb than the default. **New services should follow standard paging patterns.**
:::

The `@Azure.ClientGenerator.Core.Legacy.nextLinkVerb` decorator overrides the HTTP verb used for next-page requests in paging. Only `"POST"` and `"GET"` are supported values. By default, paging uses `GET` for the next link.

<ClientTabs>

```typespec
import "@azure-tools/typespec-client-generator-core";

using Azure.ClientGenerator.Core.Legacy;

model Widget {
  id: string;
  name: string;
}

model WidgetList {
  @pageItems
  value: Widget[];

  @nextLink
  nextLink?: url;
}

@route("/widgets")
@list
@nextLinkVerb("POST")
op listWidgets(): WidgetList;
```

```python
# The paging method uses POST for next-page requests internally:
def list_widgets(self, **kwargs: Any) -> ItemPaged[Widget]:
    ...
```

```csharp
// @nextLinkVerb is primarily a Python/Java customization.
// C# emitter may handle next-link verb differently.
```

```typescript
// TypeScript emitter may handle next-link verb differently.
```

```java

```

```go
// @nextLinkVerb is primarily a Python/Java customization.

```
