# TCGC Documentation Update

You are a documentation maintenance agent for the TypeSpec Client Generator Core (TCGC) library. Your goal is to ensure TCGC documentation stays accurate, complete, and up-to-date by cross-referencing **actual source code** against all documentation areas.

## Authoritative Sources (in priority order)

1. **Implementation source code** (`packages/typespec-client-generator-core/src` files) — this is the ultimate truth for how decorators and features actually behave, including validation rules, edge cases, default values, and error conditions.
2. **TSP declarations** (`packages/typespec-client-generator-core/lib` files) — these define decorator and function signatures.
3. **Unit tests** (`packages/typespec-client-generator-core/test/`) — these demonstrate intended behavior and edge cases.

> **CRITICAL**: Do NOT trust doc comments in `.tsp`/`.ts` files. Always verify against the related source files. Doc comments can be wrong, outdated, or incomplete — especially for decorator behavior, validation rules, and edge cases.

## Mandatory Rules

These rules are **non-negotiable** and apply to every action you take:

1. **Every `<ClientTabs>` block MUST be generated by the @doc-example-generator skill.** You must invoke the skill for each `<ClientTabs>` block you create or update — no exceptions. Never hand-write Python, C#, TypeScript, Java, or Go code inside `<ClientTabs>`. The skill compiles TypeSpec, runs all language emitters, and extracts real API surface code. Hand-written language code will be wrong.

2. **Before writing a `<ClientTabs>` block, invoke @doc-example-generator.** Do not write the block first and verify later — invoke the skill first, get the output, then insert the result. This applies to both new blocks and updates to existing blocks.

3. **One skill invocation per `<ClientTabs>` block.** Each example may have different TypeSpec input, so each block needs its own skill invocation. Do not reuse output from a previous invocation for a different example.

## Instructions

You MUST complete ALL three steps below.

### Step 1: Audit Documentation Against Source Code

**Read the actual implementation first.** Before checking any documentation, read these source files to understand current behavior:

1. **Read the source code, TSP declaration and unit tests first** — understand TCGC actual behavior: decorator logics, type graph building steps and corner cases. The implementation is the only reliable source of truth.

2. **Audit ALL documentation areas** against what you learned:
   - Decorator signatures in docs must match actual signatures in `lib/`
   - Behavioral descriptions in docs must match actual implementation logic in `src/`
   - Every decorator and public feature in source must be documented somewhere
   - No documentation should contradict the actual implementation

3. **Fix every issue found** — update signatures, fix incorrect behavioral descriptions, add missing features, mark deprecated decorators with `:::caution`. For every `<ClientTabs>` block, invoke @doc-example-generator (see Mandatory Rules).

### Step 2: Review and Fix Spector Test Coverage

This step is **mandatory**, not optional. Spector specs must cover all TCGC client customization features.

1. **Inventory existing Spector specs.** List all specs under `packages/azure-http-specs/specs/` and what features they test.

2. **Map every decorator and public feature to a spec.** Every decorator found in `src/decorators.ts` should have at least one Spector spec demonstrating its behavior. Any decorator without a spec is a gap.

3. **For each gap, read the relevant unit tests** in `packages/typespec-client-generator-core/test/` to understand expected behavior, then create a Spector spec following existing patterns and the guidelines in `.github/prompts/testserver-generation.md`.

4. **Run the full validation sequence** from `packages/azure-http-specs`:
   ```
   pnpm build && pnpm validate-mock-apis && pnpm cspell && pnpm format && pnpm lint && pnpm regen-docs
   ```

### Step 3: Finalize

> ⚠️ **IMPORTANT:** If you added or modified any Spector specs in `packages/azure-http-specs/specs/`, you **MUST** run `pnpm change add` from the repo root and add a changeset for `@typespec/azure-http-specs` with type "new feature". The CI will fail without this changeset.

Run `pnpm change add` from the repo root to record changelog entries for any modified packages.

## Quality Guidelines

When updating documentation:

1. Study existing files in the same directory before making changes — match their formatting, heading hierarchy, and code example style exactly
2. In user-facing howto docs, every code example must use `<ClientTabs>` with all six language blocks (typespec, python, csharp, typescript, java, go), even if some languages show `// NOT_SUPPORTED`
3. Every `<ClientTabs>` block MUST be produced by the @doc-example-generator skill (see Mandatory Rules) — never hand-write language tabs
4. Link to related documentation sections when referencing other features
5. Never manually edit auto-generated files (e.g., `spec-summary.md`) — use `pnpm regen-docs` instead
